## Surfaces réutilisables et frontières recommandées

**1. Projet et documents, comme accès au travail réel.** Un petit registre local référence le dossier d’app, les fichiers de mission existants, les assets choisis, commandes et URL d’aperçu. Il ne copie pas intégralement le dépôt et ne remplace ni Git ni l’éditeur. La personne ouvre les vrais fichiers avec son outil habituel. L’atelier peut démarrer vide puis conserver les productions au fil du parcours ; il ne remplit pas les étapes par avance.

**2. Choix et productions consultables.** Réutiliser le bon acquis Atelier : conserver la raison avec son contexte, distinguer actuel/historique, préparer une exploration après objection. Appliquer cela à une référence image, un cadrage ou une décision d’architecture, sans convertir l’application en variantes d’un moteur universel. Présenter un choix quand il change réellement le produit ; permettre la délégation déjà autorisée. La représentation d’un élément doit ouvrir son fichier ou son aperçu, pas un écran décoratif imitant un outil.

**3. Tâche d’agent vérifiable.** Réutiliser les formats de contexte/mission et les possibilités du host, avec une interface mince : préparation des entrées, lancement confirmé si connecté, suivi réel, retour vers diff/fichiers/tests. Le paquet garde une révision de base pour détecter les retours périmés. Une tâche peut livrer une question, un asset ou du code ; pas d’obligation à rendre `{variants}` comme aujourd’hui. Ne pas autoriser une commande arbitraire venant d’un JSON de proposition à s’exécuter silencieusement.

Les pilotes `scripts/hosts/codex-{task,rpc,meter}.mjs` contiennent déjà vie bornée, interruption et consommation partiellement réconciliée ; **ne pas les brancher tels quels comme backend produit**. Ils fixent modèle/config, fenêtres de 110/120 s, restrictions de réseau, sous-agents et hypothèses de protocole propres aux expériences. Les campagnes arrêtées et l’usage inconnu restent clos. Une connexion produit doit respecter le host existant, ses autorisations et limites, rendre les états incomplets visibles et préserver les logs pertinents. L’absence de connexion n’est pas un agent fictif à simuler.

**4. Aperçu et preuves sur l’application elle-même.** Réutiliser le serveur de développement du projet et les outils navigateur disponibles. L’atelier affiche un lien ou aperçu à URL réelle, les commandes de test exécutées et le dernier résultat lié à la révision. Il n’héberge pas le produit, ne devient pas terminal/IDE complet et ne remplace pas ses tests par le lab. Les bases de données et déploiements restent des décisions/permissions distinctes.

**5. Changement et réouverture.** L’objet à reprendre est le dossier et son application persistante, avec un paquet ciblé préparé à partir des décisions/fichiers actuels. Après modification, ne pas changer rétroactivement les anciens choix/assets/preuves. Une nouvelle tâche ou session doit pouvoir retrouver le code, la dernière référence retenue, les données métier et l’action suivante ; les liens vers fichiers non présents deviennent explicitement indisponibles.

## Plus petite tranche qui honore la chaîne demandée

Construire un parcours vertical utilisable dans le kit, puis l’utiliser pour créer une application distincte dans un **nouveau dossier sans code applicatif préinstallé**. Le choix du besoin appartient au propriétaire/à sa délégation, pas au présent audit. Le parcours fait réellement recherche/cadrage, images demandées, sélection/master, décision technique, génération de fichiers, lancement et données persistantes. Une nouvelle demande modifie ensuite un comportement de l’app et une nouvelle tâche reprend le résultat. Aucun écran ne peut se déclarer terminé parce qu’un bouton de démo a changé un enum.

Critères de sortie : (a) sources et décisions consultables ; (b) images présentes avec provenance et choix exact ; (c) app construite par une tâche réelle et ouvrable indépendamment de l’atelier ; (d) donnée créée dans le navigateur encore présente après arrêt/redémarrage ; (e) changement démontré sans perte de cette donnée ; (f) tâche suivante reprend à partir de fichiers actuels et signale une preuve périmée ; (g) même mécanisme peut ouvrir un second dossier sans modifier le code de l’atelier. Le second dossier vérifie la liaison/réutilisabilité ; il n’est pas nécessaire de refaire une longue campagne native comparative pour rendre ce mécanisme utile.

Ces critères testent la capacité et la continuité de l’expérience, pas encore la supériorité face à BMAD/Spec Kit. Pour comparer la puissance donnée à une personne, partir ensuite des mêmes besoins accessibles, laisser chaque méthode construire son contexte et compter ce travail, les choix, les corrections et l’usage réel. Ne pas donner gratuitement à l’agent témoin tout le cadrage que DevMethod prétend aider à construire ; ne pas affaiblir non plus les autres méthodes. Les corrections réelles du propriétaire sont des observations utiles, sans inventer de préférence ou bénéfice humain.

**À éviter dans cette tranche :** moteur général d’intentions, scheduler multi-agent, éditeur de code embarqué, hébergement, catalogue infini de templates, migration de toutes les missions Markdown vers un nouveau schéma, laboratoires obligatoires, badges de complétude fondés seulement sur l’existence de fichiers. La chaîne doit rester portée par les vrais objets produits et les vrais actes du host.
