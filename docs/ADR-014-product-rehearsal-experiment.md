# ADR 014 — Experiment with decisions experienced in working prototypes

Date: 2026-09-16. Status: accepted for an isolated research prototype under the user's explicit delegation to select and prototype the most promising conception. **Not adopted as the replacement DevMethod product.**

The user asks for a possible break with present operation, beyond laboratory corrections and benchmarks, while preserving project understanding, exploration, framing, design and architecture. Existing stages are already proportional. Repackaging them in a dashboard would not answer this request.

The alternatives are [change transactions, executable product rules and an intent/dependency model](missions/product-alternatives/CONCEPTIONS.md). Current products already offer planning, visual alternatives, annotations, agent coordination and persistent project knowledge: see the dated [primary-source inventory](missions/product-alternatives/PRIOR-ART.md). None of these features alone differentiates DevMethod.

Select **executable behavioral alternatives** for a first usable experiment. The user tries the same situation across working prototypes, keeps a choice with its actual observations and reason, changes the need, and exercises an agent proposal without losing the records. Its main unit is an experienced decision. Hypothesized value: make an implicit preference discussable and keep it usable through change. This is unproven against ordinary prototypes plus conversation.

The experiment uses a data-only finite-state domain, Node HTTP/persistence and a browser UI. The domain validates and executes rules; storage commits atomically before acknowledgment; the UI uses text nodes and native controls. Each component owns one boundary. No expressions, generated code execution, arbitrary shell, automatic provider dispatch or external publication. Project revisions reject outdated proposals; storage versions reject stale tabs. A request is an actual local file for a host agent, not a pretend background job. An agent in this task exercises that boundary.

This boundary supports choices about authority and transitions. It cannot establish content quality, factual review, collaboration, arbitrary application generation or production architecture. Design and architecture statements are proposed explanations, not deductions proven by this engine. Understanding remains editable context; exploration retains questions/sources and agent handoffs; framing retains constraints; design changes the organization of the same working data; architecture exposes intended boundaries and unresolved tradeoffs. None is replaced by a hidden mandatory document step.

The adapter is deliberately disposable and separate from the installed stage commands. It adds `npm run atelier` for repository/package experimentation and does not alter the six skill modules, installed CLI API, release version or external state. The baseline can use the same data, options and ordinary tools without this surface. See the [prospective experiment](missions/product-alternatives/EXPERIMENT.md) for rejection criteria. If the bounded model fails on the independently authored context, preserve that failure, reassess transactions/dependencies, and continue useful work instead of converting the mission back into benchmark maintenance.
