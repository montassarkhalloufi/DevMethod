## Conclusion utile

Les trois produits couvrent déjà une large partie du parcours demandé. Un chat avec preview, sélection d'élément, sauvegarde Git et bouton Revert ne différencie pas DevMethod. Dyad est l'alternative locale pertinente : app et sources locales, modèles interchangeables, code inspectable. Il offre un comparateur fort pour toute promesse de contrôle ou d'absence de dépendance au cloud propriétaire.

Le problème restant le plus concret est de **savoir quel état on conserve en changeant de workflow** : code sauvegardé ou seulement affiché ; historique disponible après branchement Git ; données, identités et secrets conservés ou à recréer après export. C'est une possibilité à éprouver, pas une lacune universelle démontrée.

## Constats précis de continuité

**Base44 : frontière d'historique explicitement documentée.** Après connexion GitHub, Version History ne peut plus restaurer les versions antérieures, absentes du repo. Ce n'est pas un témoignage : c'est l'avertissement du [guide officiel](https://docs.base44.com/developers/app-code/local-development/github). Un builder qui promet la continuité doit afficher cette conséquence avant connexion. L'export et la possession du code ne remplacent pas la migration des données/auth/configuration. La promotion « rien n'est verrouillé » est plus large que le parcours `eject` documenté.

**Données : ne pas annoncer un trou déjà comblé.** Base44 dispose de snapshots d'entités ; Dyad/Portal d'undo DB. La question non établie par ces pages est une opération coordonnée code+schéma+records+auth sur toute intégration, avec préservation des nouvelles données. Il faut limiter toute promesse DevMethod au backend réellement pris en charge. Git + dump + migration testée est un témoin ordinaire fort.

## Pratiques à reprendre, hypothèses à éprouver

1. **Fondation nécessaire, déjà existante ailleurs** : une vraie app visible rapidement ; retouche d'élément sans reformuler toute la page ; mode discussion distinct de l'application ; état enregistré/synchronisé explicite ; retour arrière déterministe au lieu d'un prompt d'annulation. Ce sont des critères d'utilisabilité, pas une rupture DevMethod.
2. **Petite expérience utile de continuité** : sur le vrai projet courant, produire un paquet de reprise qui conserve code, changements manuels, décision courante et instructions de lancement ; le rouvrir dans un dossier neuf et effectuer une petite modification. Mesurer les faits perdus, actions manuelles et services requis. Comparateur : repo+README+Git+bonnes notes fourni avec le même accès. Aucun humain simulé ; succès objectif de transfert uniquement, effort humain encore inconnu.
3. **Hypothèse de guidage**, non validée : avant une action qui change le support de l'app (Git/export/backend), présenter ce qui sera conservé et ce qui devra être recréé, dérivé de l'état réel et vérifié par un essai local. Plus petit produit : panneau « ce qui repart avec vous » avec export concret et reprise vérifiée. Réfutation : le parcours natif équivalent conserve déjà tout aussi clairement, ou notre paquet nécessite autant de reconstruction que le témoin. Ne pas élargir cela en moteur universel de migrations.

Limites : cette recherche ne mesure ni qualité de première génération, ni fidélité visuelle, ni sécurité des apps, ni coût total pour terminer. Aucun « essai réel » de ces produits dans cette sous-tâche ; les témoignages restent attribués. Les campagnes antérieures restent closes.
