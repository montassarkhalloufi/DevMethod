# Working modes and scoped intervention

Use when a collaboration boundary must be established, changed or repaired. Reuse
the user's stated preference, accepted decisions and current authorization before
asking. An older profile with equivalent wording keeps its recorded meaning; a
new label must not silently expand its delegation.

## Three modes, the same quality

| Mode | Decision authority | Delivery behavior |
|---|---|---|
| Autonomous | Choose reversible product, design and technical options inside the explicit delegation, recording consequential choices and their reasons. Escalate only what exceeds it. | Carry the authorized work through usable implementation, verification and review; report results and limits without inventing a required acceptance ceremony. |
| DevAuto | Prepare credible structural alternatives, recommend a choice and obtain acceptance of the relevant scope and constraints before dependent realization. Reuse prior acceptance. | Implement and verify that accepted scope automatically when the host permits it; apply bounded corrections, retain evidence and show the usable result. |
| Guided | Discuss material choices and agree useful checkpoints for accepting the result. The user steers outcomes rather than coordinating roles, commands or files. | Prepare each authorized slice through implementation, verification and review before seeking its acceptance. Progress independent work while a consequential decision is pending. |

All modes retain the same repository checks, visual and interaction verification
where applicable, review requirements, data preservation and evidence standards.
Generation is not verification; a check passed on an older revision does not prove
the changed result. A mode does not grant purchases, external contact, publication,
deployment or integration permissions absent from the session. Missing tools and
unmeasured costs remain explicit. These instructions can guide different hosts;
they do not prove unattended execution or portability on a host that was not tried.

## Apply the boundary to the actual change

Use the existing profile to record mode, source and the meaningful boundaries of
delegation. A structural choice changes an accepted outcome, major user journey,
visual direction, data contract, dependency or operating commitment. A local
implementation detail that preserves those choices normally stays delegated.
Classify by consequence, not by file type or the stage's name.

Mode defaults yield to the user's explicit instructions. Delegation can differ by
decision: “choose the product and technical approach, but show visual proposals
before implementing the interface” delegates the former even in guided mode and
reserves the latter even in autonomous mode. Record the relevant exceptions,
their source and scope beside the mode in the existing context. Do not ask again
about delegated choices or infer acceptance of reserved ones.

Where those defaults still apply, in DevAuto present the concrete proposal and
unresolved trade-off before the dependent realization. In guided mode, show the
useful result and checks before
its acceptance checkpoint. Approval already provided in the conversation or
canonical record is sufficient; do not demand a ritual command, a document at
every stage or repeated approval for each repair. A bounded stage request keeps
its own scope: selecting a mode does not start unrelated backlog work.

When a new observation changes an accepted need or constraint, identify the
affected decision, reference or evidence. Preserve its history and revisit only
the dependent work. Reversible choices inside explicit delegation can be revised
by the agent in any mode. Discuss replacements for choices still reserved to the
user before dependent implementation. Unaffected acceptance and valid evidence survive.
Use the existing correction procedure when present; keep a short change short.

## Distinguish preference, acceptance and reopening

When visual approval is reserved, present concrete proposals in the requested
medium, let the user choose, then implement the dependent interface and verify
its fidelity. A proposal, a positive comment, a selected filename or an agent's
recommendation does not by itself establish that approval. Record what the user
actually accepted: a composition can be accepted while typography, imagery or
color remain open. Explicitly delegated visual choices can be made by the agent;
record them as delegated decisions, not as human validation.

If the user reopens a previously accepted aspect, preserve the history and mark
that aspect open before relying on it again. Do not override the new instruction
with the old approval or invalidate unrelated decisions. Prepare new proposals
for the reopened scope; continue authorized research, backend work and checks
that do not depend on the pending choice. Silence or time elapsed is not a choice.

Keep proposed, accepted, reopened and superseded states understandable in the
existing records without requiring a new document at each transition. Reconcile
the host's actual stored state when necessary: a conversation instruction does
not prove that an application's approval record was updated. State that limit
instead of inventing an automated approval or revocation mechanism.

## Observe drift, then act within bounds

Set proportionate execution and correction bounds before a costly or repeating
operation, using the project's existing policy and the actual available budget.
Do not invent a universal retry count, cost estimate or quality score.

| Observable signal | Consequence and next action |
|---|---|
| A required check fails or the running product contradicts an accepted criterion | Keep the failure visible, localize its cause and correct the affected slice within the agreed bounds. A single recoverable failure need not interrupt the user. |
| The same failure persists across attempted corrections, or work repeats without new evidence | Stop the repeating operation at its agreed bound, preserve the attempts and inspect a different hypothesis. Seek a scoped decision if further progress requires a changed constraint or delegation. |
| A changed requirement, reference, dependency or revision invalidates context used for work | Identify affected decisions and checks; reconcile them before relying on that context. Do not restart unrelated stages. |
| Consumption becomes unknown, a quota is reached or a capability disappears | Suspend dependent costly calls or unavailable actions. Preserve known usage separately from the unknown total, report the limit and continue independent authorized work. Do not reopen a stopped budget under another task name. |
| The next action exceeds delegation or requires an ungranted external permission | Prepare a concrete reviewable proposal and ask for that action only. Time elapsed or silence is not authorization. |

A drift report names the observed fact, supporting artifact or failed check,
affected scope, attempts already made, remaining uncertainty and recommended next
decision. Do not turn these facts into an unsupported confidence percentage. Human
intervention resolves the specific boundary; it does not hand all coordination
back to the user. If no human decision is needed, make the bounded correction and
report its result.

## Interruption and resumption

Keep mode and delegation beside the project's existing canonical context, linking
the accepted outcome, selected design, architecture, active decisions, current code
and applicable evidence. Record interrupted work and unresolved signals without
claiming success. On resumption, inspect what actually changed, recover the next
authorized slice and retain valid choices. Reconcile a changed authorization or
budget only where it matters; do not re-ask the whole startup questionnaire.

The number and format of records follow the project's conventions and
[work sizing](work-sizing.md). This contract requires understandable state and
evidence, not a new dashboard, provider adapter or fixed set of documents.
