# Product maturity evaluation

Use this corpus to examine decision quality and technical evidence beyond a bounded implementation exercise. [cases.json](cases.json) contains reusable requests and synthetic input files. It neither executes agents nor establishes comparative results. The review fixture is intentionally defective; its handoff includes claims to evaluate, not trusted validation.

The additional [architecture cases](architecture-cases.json) distinguish unknown workload from fully supplied targets, compare visual alternatives and estimated costs, and exercise scope coverage plus a tiny UI change. Evaluate spontaneous elicitation separately from using numbers already supplied. Architecture-only requests do not authorize benchmarks or establish runtime capacity; operating targets may conflict with staffing even when both are stated in the brief.

## Run conditions

Pin the method revision, actual installed skill files, task and input files before each attempt. Use real `init` resources rather than an incomplete skill copy. Start each attempt in a fresh conversation and exclusive directory; a shared filesystem is not a security sandbox. Allow the same tools, source access, permissions and side effects in every comparison arm. Keep the review oracle and prior outcomes outside worker inputs. Preserve requests, returned questions and any supplied answers.

Compare reference, candidate and no-method conditions with matched briefs. A no-method arm retains system/tool instructions and safety controls. Use repeated cases (initially three per cell) and randomize order where practical; explain sequential or unmatched conditions. Neither a specialist agent nor its score is an expert-human comparison. To claim superiority over human experts, a separately designed, consented comparison with qualified people would be needed.

## Observable outcomes

| Scenario | Required substance |
| --- | --- |
| Open product idea | Preserves ambition, actors and undelegated decisions; compares credible directions on decisive criteria; separates vision, prototype/pilot and commercial readiness; explains what a first slice teaches and what it cannot establish |
| Architecture and data | Decisions follow team/operating constraints; tenant/site/assignment authorization and data visibility are explicit; model and transaction boundaries protect invariants; migration ambiguity, reconciliation and return-path writes are handled |
| Real delivery | Documented service runs; capacity and idempotency hold across independent processes; cancellation releases capacity once; migration preserves IDs/statuses, rejects invalid input atomically and does not modify originals |
| New design | Evaluate actual generated alternatives, selected master, reference-conditioned derivatives and working prototype separately; new defaults and explicit user overrides are distinguished; aesthetic examples are not scientific evidence |
| Evidence review | Recognizes the valid narrow test, reproduces concrete defects where possible, rejects unsupported broad validation, and preserves read-only scope |

Add transfer cases before general claims: same ambition with a different user expertise level, a change under an approved design identity, and a fresh resumption after a contract change. Preserve the original requirements rather than making the novice's task easier. Assign dimensions before running each case; do not invent hidden requirements or move a failed criterion to N/A afterward.

## Assessment and stopping

For each applicable dimension, record absent/incorrect, superficial, adequate/argued, or deeply verified, with artifact or execution evidence. Use dimensions such as business understanding, ambition, communication, design, architecture, data, operation, verification, resumption and proportionality. Do not average away a material data loss, unauthorized access, fabricated evidence or silent removal of a central requirement. Separate new target expectations from obligations actually present in an older method.

An independent reviewer should inspect artifacts and rerun decisive behavior, not score headings, test counts or eloquence. Anonymize conditions when feasible and disclose remaining cues. Prefer targeted counterexamples: concurrent last-capacity requests, repeated migration, history failure or a claimed browser check with no browser evidence. Check that a test can fail when a relevant invariant is violated. Do not add exhaustive unrelated audits to minor changes.

Preserve original failures and separate repaired attempts. Generated images, author-written summaries, real browser interactions, database experiments and installer tests are different evidence types. Author RESULT.md files are not complete native tool transcripts and do not prove historical stage ordering. Missing tools remain missing; blocked image/browser work is not success or permission to bypass controls. Record tokens and cost only when exposed.

Stop after scoped verification or a concrete blocker; add attempts to resolve an identified uncertainty, not an arbitrary count. Raw host outcomes remain private under [the evaluation policy](../../docs/EVALUATION.md). Publish only explicitly authorized, pinned results with limitations. No universal reliability, expert superiority or productivity advantage is established by this corpus.

[Portable-study scenarios](portable-cases.json) cover first-mode choice, preference changes, complete/incomplete PDF or DOCX export and resumption from an actual source package. The document/import entries describe required fixtures rather than providing a turnkey exporter or executable corpus. Inspect actual embedded visuals, source links, scope coverage and imported evidence; filenames or a complete-looking table of contents are insufficient.
