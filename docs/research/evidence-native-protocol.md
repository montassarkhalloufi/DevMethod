## Three mandatory arms

| Arm | Inputs and intervention |
| --- | --- |
| Strong simple baseline | Same best available authorized model, tools and explicit product brief; normal tests, Git and a clear instruction to verify and report uncertainty |
| Same baseline plus independent checks | Identical external acceptance assertions and fault controls available to the lab, but ordinary execution and Git; isolates the benefit of better tests |
| Same baseline plus optional evidence lab | Same checks and authoring information, plus permit, qualification, freshness and correction journal; tests the incremental lifecycle value |

Native DevMethod 0.5, BMAD v6.12.0 and a documented planner/generator/evaluator harness are additional candidates, not fictional implementations to label as competitors. Add an arm only after pinning its real version, prerequisites and matched budget. The [landscape](evidence-landscape-2026-09-15.md) explains why comparison with outdated or badly configured competitors is not informative.

## Freeze before admitting the first call

Record exact host executable and model versions, reasoning setting, OS, authentication method without credentials, tool permissions, method archive/hash, code/checker/control/brief hashes and timestamps. Verify the actual cancellation/accounting adapter. Unknown model identity, unavailable usage or incomplete prior execution blocks admission.

Use two separately authored product tasks, each including initial delivery, a new-session requirement change, persistence/restart and regression assessment. Keep their held-out outcomes outside the producer's assigned root, with equal relevant task information in every arm. The current capacity/invoice/queue cases have been inspected during research and must not become a claimed fresh generalization set. An external reviewer must judge the delivered product, including visual usability where relevant.

Initial proposed budget: **12 paired episodes, 24 invocations maximum** = two tasks × three arms × two repetitions × two sessions (initial delivery and later change); one invocation at a time; at most 180 seconds and 2 MiB output per invocation. The maintenance session is explicitly counted, including when initial delivery fails. Rotate arm order with a recorded seed before execution. No selective reruns. No purchases, provider fallback or unapproved calls. Admission still requires the missing host/model/fixture/accounting pins above; this document dispatches nothing.

Use the existing supervisor's supported local hard limits. An initial **500,000 observed-token inter-run threshold** is a proposed admission stop, not a hard in-flight provider cap or a user-approved spend amount. Unknown usage, interruption or the threshold crossing blocks the next invocation for reconciliation. Record actual dollars only if the provider supplies trustworthy accounting. Charge checker/control authoring, setup and review separately; do not call them free because the fixture is already supplied.

## Outcomes fixed before comparison

Primary: all independent critical product behaviors pass after delivery and after change. Separately count false completion, missed regressions, unsupported/stale evidence, scope violations, useful decisions, interruptions, elapsed time, tokens/cost, required review time and lines/dependencies maintained. A failed, interrupted, not-run or unusable product stays in its original slot and denominator.

Report paired outcomes per task/repetition and every loss. Do not aggregate process, correctness and aesthetics into an arbitrary score. A small pilot can justify a larger study; it cannot establish statistical superiority or a universal ranking. If good independent tests match the lab while costing less to set up, operate and review, prefer those tests. Reopen the radical product-search design only with real preference evidence that an early alternative changes a consequential product choice.
