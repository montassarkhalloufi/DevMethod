# Lovable — connecteurs et carte des configurations

Recherche documentaire officielle du **17 septembre 2026**. Ce rapport distingue les contrats décrits par Lovable, les inconnues et les suggestions pour DevMethod. Il complète l’inspection de l’interface menée séparément ; il ne constitue pas son compte rendu.

**Actions réalisées :** consultation des pages publiques officielles et de leurs représentations Markdown, découverte des rubriques par l’[index documentaire officiel](https://docs.lovable.dev/llms.txt), rédaction de ce fichier. Aucun compte connecté, secret saisi, outil MCP exécuté, script d’application lancé, message envoyé, achat, provisionnement ou publication. Aucun test de fonctionnement d’un fournisseur. Les fonctionnalités de catalogue ne sont pas autant d’intégrations vérifiées.

La carte couvre les familles de configuration documentées et les limites importantes ; elle ne certifie pas l’exhaustivité des options conditionnelles de chaque fournisseur, plan, version de projet ou déploiement progressif. Aucun prix n’est figé ici.

## 1. Ce que désignent les différents connecteurs

Un même service peut proposer plusieurs modes dans le catalogue. Le choix porte sur **qui agit, avec quelle identité et à quel moment** ; le nom du fournisseur ne suffit pas. Les connexions de projet et celles de chat sont présentées séparément. Les actions d’ajout avancé sont accessibles depuis l’accueil du catalogue. [Présentation officielle](https://docs.lovable.dev/integrations/introduction).

| Mode                     | Consommateur et identité                                                         | Configuration et portée                                                                     |
| ------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **App + chat**           | Agent pendant la construction et application publiée ; compte fournisseur commun | Connexion du workspace, liée aux projets autorisés                                          |
| **App user**             | Application au nom de chaque utilisateur final                                   | Client OAuth commun ; autorisation individuelle de chaque utilisateur                       |
| **Chat / MCP**           | Agent Lovable avec le compte personnel du constructeur                           | Connexion personnelle pour le contexte et les actions du chat ; pas une intégration runtime |
| **Custom API connector** | Même usage App + chat, pour une API REST définie par le workspace                | Définition réutilisable, puis création de connexions                                        |
| **Custom MCP server**    | Agent Lovable appelant les outils d’un serveur externe                           | URL et authentification personnelle                                                         |
| **MCP registry**         | Membres parcourant un annuaire de serveurs                                       | Découverte partagée ; connexion et authentification séparées par membre                     |

Les trois premiers modes sont définis dans l’[introduction](https://docs.lovable.dev/integrations/introduction), les extensions dans [Custom connector](https://docs.lovable.dev/integrations/create-connector), [Custom MCP](https://docs.lovable.dev/integrations/custom-mcp) et [MCP registries](https://docs.lovable.dev/integrations/mcp-registries).

### App + chat : compte commun et liaison aux projets

La connexion OAuth ou par credentials appartient au workspace. Elle peut servir plusieurs projets, après liaison et implémentation de l’usage.

La connexion ordinaire est **privée par défaut**, partageable à certains membres ou au workspace. L’option « Managed by Lovable », lorsqu’elle existe, est partagée par défaut et limitée à une connexion gérée par connecteur/workspace.

L’agent lit sans confirmation ; les mutations proposent accord ponctuel, persistant ou refus. L’accord persistant dépend de la personne et de la connexion. Réglages : projets liés, partage, permissions, déliaison et suppression. Délier conserve la connexion ; supprimer retire ses identifiants et casse les usages dépendants. Un remix ne recopie pas les connexions.

Le compte fournisseur utilisé et ses droits déterminent les données accessibles. Une permission accordée au constructeur n’est pas un contrôle d’accès des utilisateurs finaux. [App + chat connectors](https://docs.lovable.dev/integrations/app-connectors).

### App user : client commun, comptes individuels

Le constructeur configure un client OAuth du workspace, privé initialement, puis le lie au projet. Chaque utilisateur de l’app consent avec son propre compte. La passerelle vérifie son rattachement utilisateur/projet/workspace, injecte et renouvelle ses jetons, sans les exposer au code ni aux constructeurs. L’app doit identifier l’utilisateur ; la réutilisation d’identité Lovable constitue un cas particulier pour certaines apps internes.

**Builder access** ajoute une autorisation personnelle du constructeur, limitée au projet et révocable séparément. Elle ne transmet pas son compte à l’app ou aux collègues ; les données retournées peuvent toutefois entrer dans le chat partagé. Les écritures demandent normalement confirmation ; une lecture transportée par POST peut aussi la demander.

L’accès hors session est activé par défaut : réglable en Business/Enterprise, toujours activé en Free/Pro, avec déploiement progressif du contrôle. Il faut délier tous les projets avant de modifier ce choix. Déconnecter un utilisateur révoque ses jetons ; supprimer le client affecte tous ses utilisateurs.

Le tableau officiel couvre Google, Microsoft, GitHub/GitLab, Slack, Salesforce, HubSpot, Linear, Notion et plusieurs plateformes de données/entreprise, avec prérequis propres. [App user connectors et configuration OAuth par fournisseur](https://docs.lovable.dev/integrations/app-user-connectors).

### Custom API connector : définition REST réutilisable

Création par propriétaire/admin, tous plans. Trois groupes : identité et présentation, authentification, connaissances de l’agent. La définition comprend nom, identifiant stable, descriptions, logo facultatif, catégorie, documentation, base HTTPS et requête de vérification des identifiants.

Six schémas sont documentés : Bearer, en-tête personnalisé, paramètre de requête, Basic, plusieurs champs avancés, OAuth 2.0 authorization code. Les champs avancés distinguent valeurs secrètes et publiques ; OAuth expose endpoints, scopes, séparateur et PKCE. L’URL de retour affichée doit être reprise exactement chez le fournisseur. Les secrets sont renseignés lors de la connexion, pas dans la définition.

Les fichiers de connaissances décrivent endpoints, schémas, pagination et contraintes. Ils sont distincts des instructions du projet. La création alimente le catalogue **App + chat** ; la génération d’un connecteur App user arbitraire n’est pas documentée.

La définition reste modifiable, avec restrictions sur le changement de famille d’authentification et les clés de champs existants. La supprimer supprime aussi ses connexions et secrets. [Créer un connecteur personnalisé](https://docs.lovable.dev/integrations/create-connector).

### Chat MCP, serveur personnalisé et annuaire

**Chat MCP.** La connexion est personnelle : chaque membre autorise son compte et gère son accès. Elle sert l’agent pendant la construction, sans fournir automatiquement le service à l’app publiée. MCP n’implique pas lecture seule : certains outils peuvent modifier des objets. Les prérequis varient, par exemple activation MCP et exposition des workflows côté n8n, ou données préalablement instrumentées côté analytics. Le catalogue documente notamment Notion, Linear, Atlassian, Miro, Canva, n8n, Sentry et d’autres outils. [Chat connectors](https://docs.lovable.dev/integrations/chat-connectors).

**Custom MCP.** Configuration par nom, URL et OAuth, jeton Bearer/API key ou absence d’authentification. Connexion distante directe par défaut. La sortie par IP statique est une option Enterprise à activer avec Lovable, uniquement pour les serveurs personnalisés éligibles ; pas pour les connecteurs intégrés ni ceux d’un registre. Le choix est fixé à la création : changer impose une nouvelle connexion. Une liste IP ne remplace pas l’authentification. La documentation ne garantit pas ici tous les transports/versions MCP possibles. [Custom MCP server](https://docs.lovable.dev/integrations/custom-mcp).

**MCP registry.** Un propriétaire/admin ajoute un annuaire compatible avec la spécification communautaire, son URL, éventuellement un nom et un Bearer d’accès. Ce jeton ouvre l’annuaire, pas chaque serveur. Tous les membres peuvent parcourir ; editors et supérieurs peuvent connecter. La connexion serveur demande ensuite son propre OAuth/jeton/accès public. Une même URL de registre ne peut être ajoutée deux fois au workspace. Recherche, défilement, indication d’origine et édition/suppression du registre sont disponibles. Supprimer l’annuaire conserve les connexions déjà créées ; le rajouter les rattache. Les serveurs distants importés restent directs, sans option IP statique. Les entrées locales nécessitent Desktop ; certaines entrées incompatibles sont masquées. Aucun annuaire par défaut n’est fourni. [MCP registries](https://docs.lovable.dev/integrations/mcp-registries).

**MCP local.** Desktop peut connecter des outils locaux détectés, un processus avec commande/arguments ou un serveur HTTP local. Premier accès soumis à approbation, retrait possible dans les réglages. L’agent nécessite toujours Internet. Les politiques remote MCP et local Desktop doivent toutes deux autoriser cet usage. [Application Desktop](https://docs.lovable.dev/integrations/desktop-app).

### Permissions de connexion et secrets

En Business/Enterprise, les admins règlent séparément la création de connexions/clients : personne, admins, ou editors et admins. Les valeurs initiales varient : Free/Pro permettent editors+, Business privilégie admins, Enterprise interdit initialement les connecteurs ordinaires concernés. Les définitions personnalisées suivent un défaut admin distinct. Certains services intégrés ont simplement un interrupteur.

Changer qui peut créer ne révoque pas nécessairement les connexions existantes. Le partage d’une connexion vise des membres du workspace, pas des collaborateurs externes. Les contraintes de connexion peuvent limiter l’accès à un projet pendant sa construction, **mais ne sont pas appliquées comme ACL des visiteurs après publication**. Les connexions Chat restent personnelles. [Administration des connecteurs](https://docs.lovable.dev/integrations/admin-controls).

La passerelle chiffre les identifiants, non relisibles intégralement par membres, admins ou agent. L’app utilise une clé projet LOVABLE_API_KEY et une référence opaque de connexion. OAuth est renouvelé automatiquement. La limite annoncée est **1 000 requêtes/minute/connecteur/projet** pour cette passerelle ; ne pas l’étendre aux autres chemins. Certains connecteurs n’y passent pas et certaines clés sont volontairement publiques. Après rotation, une ancienne clé projet peut rester valable jusqu’à une heure. Les connexions inutilisées ne sont pas supprimées automatiquement. Les plages réseau des connecteurs gateway diffèrent de celles du MCP personnalisé à IP statique. [Sécurité des intégrations](https://docs.lovable.dev/integrations/security).

| Stockage/configuration    | Usage et limites                                                                                                                                                                                                                                                              |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identifiants de connexion | Gérés par la connexion et la passerelle ; ne pas les confondre avec des variables du projet. [Sécurité](https://docs.lovable.dev/integrations/security)                                                                                                                       |
| Secrets du projet         | Backend/runtime, écriture sans relecture ; ajout/remplacement/suppression, noms visibles. Les secrets manuels ne suivent pas un remix. Les variables VITE_ sont publiques et ne sont pas des secrets backend. [Secrets](https://docs.lovable.dev/features/secrets)            |
| Secrets de build          | Enterprise, workspace entier, injectés pendant installation/build ; gestion admin/propriétaire, noms accessibles aux editors. Ils ne remplacent pas les secrets runtime et ne sont pas isolables par projet. [Build secrets](https://docs.lovable.dev/features/build-secrets) |

Une API intégrée directement reste une quatrième possibilité : appel public sans secret, ou backend généré et secret de projet si authentification. Fournir méthode, URL, headers et contrat de réponse aide la génération ; cela ne crée pas automatiquement une connexion personnelle MCP. [Intégration de toute API](https://docs.lovable.dev/integrations/any-api).

## 2. Trois sens MCP à ne pas confondre

| Sens                                             | Produit             | Pouvoir réel                                          |
| ------------------------------------------------ | ------------------- | ----------------------------------------------------- |
| Service externe → agent Lovable                  | Chat connectors     | Lire ou agir dans un outil pendant la construction    |
| Agent externe → Lovable                          | Serveur MCP Lovable | Créer/modifier/gérer des projets Lovable              |
| Assistant d’un utilisateur → application publiée | Agent integrations  | Appeler les opérations exposées par cette application |

Le serveur **mcp.lovable.dev** utilise OAuth, sans API key de substitution. L’autorisation porte sur le compte et les projets accessibles à cette identité, pas seulement un projet choisi. Des outils peuvent publier ou exécuter du SQL modifiant données/schéma. Les permissions du membre et les règles du workspace s’appliquent ; les clients hébergés peuvent nécessiter l’approbation de leurs redirections OAuth. Ce n’est donc pas une simple recherche documentaire. La création de connexion via add_connector renvoie vers l’interface, sans réaliser la connexion elle-même. [Serveur MCP Lovable](https://docs.lovable.dev/integrations/lovable-mcp-server).

La référence publique liste ces familles d’outils, **sans exécution dans cette recherche** :

- Identité/workspaces : get_me, list_workspaces, get_workspace.
- Projets : create_project, list_projects, get_project, deploy_project, remix_project, set_project_visibility, set_folder_visibility, move_projects_to_folder, render_project_widget.
- Agent : send_message, get_message, list_messages.
- Code : get_diff, list_files, read_file, list_edits.
- Contexte : get_workspace_knowledge, set_workspace_knowledge, get_project_knowledge, set_project_knowledge.
- Base : get_database_status, enable_database, query_database.
- Fichiers : get_file_upload_url.
- Catalogue : list_connectors, add_connector.
- Réutilisation : list_template_projects, list_design_systems.
- Mesures : get_project_analytics, get_project_analytics_trend.

Cette liste reflète la [référence publique du serveur](https://mcp.lovable.dev/skill.md), pas une découverte authentifiée des outils du compte. Elle décrit aussi pagination, interrogation asynchrone, paramètres de révision et déduplication limitée des appels de création/message. La page produit mentionne des outils supplémentaires de skills/connexions : l’inventaire exact doit donc être découvert à l’exécution, pas déduit de cette seule liste.

**Application publiée en MCP.** Lovable génère outils et endpoints ; la publication les rend actifs. OAuth est le défaut, accès anonyme un choix explicite, global à l’intégration. Le backend doit contrôler propriétaire, rôle et abonnement : masquer un bouton ne protège pas un outil. Les apps internes exigent l’authentification ; leur session applicative reste distincte de l’appartenance au workspace. Les appels utilisent le vrai backend, sans plafond de dépenses ni limitation automatique propres à cette fonctionnalité. Les changements d’outils exigent publication puis rafraîchissement côté client. Les tâches longues peuvent expirer, les alertes spontanées vers l’assistant ne sont pas prises en charge, et il n’existe pas d’annuaire public de découverte. Retirer l’application publiée retire son serveur. [Agent integrations](https://docs.lovable.dev/features/agent-integrations).

### Cloud et exploitation

Cloud fournit base, identité, stockage, fonctions et observabilité. Le choix d’un Supabase externe est distinct. Les permissions de l’agent couvrent activation, lectures base/analytics/logs/configuration, contrôles, migrations, ajout de données et configuration d’auth. Les trois réponses possibles sont toujours autoriser, demander ou interdire ; la documentation indique **autorisation automatique par défaut**.

Régions générales : Americas, Europe, Asia Pacific. La région devient fixe après activation ; politique imposée Business/Enterprise, régions spécifiques Enterprise sur demande. Pas de migration Supabase→Cloud ni de migration Cloud→Supabase en un clic. Retirer Cloud détruit son instance ; exporter auparavant relève d’un autre acte. [Lovable Cloud](https://docs.lovable.dev/features/cloud).

### AI et paiements applicatifs

**AI runtime.** Le connecteur AI sert les fonctionnalités de l’app, pas le modèle constructeur. Activation et permissions de l’agent sont réglables ; appels backend avec clé projet gérée, streaming possible. Choix de modèles pour texte, image, vidéo, embeddings et audio. Le dashboard expose statut, durée, modèle, tokens et consommation. Les métriques restent disponibles sans contenu ; l’option AI app context conserve requêtes/réponses expurgées de secrets jusqu’à 90 jours, activée par défaut Free/Pro et désactivée Business/Enterprise. Consultation historique : 24 h Free, 90 jours payants. Limites de fréquence au workspace, erreurs 429 ou 402 selon saturation/budget ; concurrence vidéo documentée d’un clip Free, dix payants. Les références de modèles changent : consulter le tableau courant. [AI features](https://docs.lovable.dev/features/ai).

**Paiements.** Intégration gérée Stripe ou Paddle, Pro+, setup par admins/propriétaires de projet/workspace. Conditions backend différentes entre TanStack et ancien React/Vite. Prévisualisation en test, production en live ; produits/prix synchronisés à publication, vérification fournisseur nécessaire avant encaissement. La vue expose transactions, abonnements, ajustements, métriques et checklist live. Style/moyens de paiement restent partiellement chez le fournisseur. Un fournisseur par projet et, par défaut, un abonnement par utilisateur/environnement ; remix interdit après activation.

Déconnecter retire secrets et intégration, bloque checkout/synchronisation et ne permet pas de reconnecter le même compte au même projet. Cela **n’annule pas les abonnements chez le fournisseur**. Changer de fournisseur ne migre pas produits, abonnements ni historique. Les webhooks générés ont des rôles distincts pour l’app et le monitoring. Ces opérations n’ont pas été essayées. [Payments](https://docs.lovable.dev/features/payments).

## 5. Disponibilité, divergences et inconnues

- **Documentation récente contre indexation ancienne.** Certaines versions de résultats de recherche utilisent encore « app only » ou un partage généralisé. Les pages produit directement consultées décrivent App + chat et une connexion ordinaire privée initialement. La disponibilité visible dans le workspace doit rester une observation séparée. [App + chat](https://docs.lovable.dev/integrations/app-connectors).
- **Référence MCP moins actuelle sur certains détails.** Le document du serveur affirme encore que les paiements intégrés requièrent Cloud ; la page Payments distingue désormais les stacks. Les listes d’outils des deux pages diffèrent aussi. Pour ces prérequis, privilégier la page spécialisée, puis le comportement observé, sans supposer leur concordance. [Référence MCP](https://mcp.lovable.dev/skill.md), [Payments](https://docs.lovable.dev/features/payments).
- **Bêta et rollout.** « Managed registry » désigne le registre npm Enterprise en Beta ; ne pas attribuer ce statut par analogie au registre MCP. Une mention Beta dans le compte réel peut concerner une autre version de fonctionnalité. [Registre npm](https://docs.lovable.dev/features/managed-registry).
- **Plans.** Les mentions Free/Pro/Business/Enterprise viennent des pages fonctionnelles datées par cette consultation. Les droits contractuels, quotas détaillés, extensions et disponibilités du compte peuvent différer. Pas de tarif, remise ou capacité garantie déduite ici. [Plans officiels](https://docs.lovable.dev/introduction/subscription-plans).
- **Secrets et données.** Chiffrement et non-relecture ne documentent pas à eux seuls algorithmes, KMS, résidence de tous les flux, rétention complète des données de connecteurs, TTL de chaque token ou isolation interne. Les données retournées dans le chat sont une surface distincte des credentials. Une région Cloud ne prouve pas la résidence de tous les sous-traitants.
- **Permissions.** Ne pas inférer le droit d’utiliser toutes les connexions privées du seul rôle admin. Les droits de création, partage, suppression, invocation, publication et accès utilisateur sont distincts. Les scopes exacts exigent le fournisseur et l’écran de consentement réel.
- **MCP.** Aucun handshake authentifié, inventaire runtime, transport exact, plafond par outil ou garantie d’idempotence des actions fournisseur n’a été vérifié. Un répertoire compatible ne prouve pas que chaque serveur fonctionne.
- **Couverture.** La carte recense les réglages documentés par famille ; elle ne contient ni tests de chaque fournisseur, ni audit de sécurité, ni vérification juridique, ni certification des comportements du compte.

## 6. Suggestions d’architecture pour DevMethod — à discuter séparément

Ces suggestions sont des **inférences de conception**, pas des fonctionnalités déclarées livrées ni une autorisation d’étendre le chantier.

1. **Séparer les consommateurs dans le modèle.** Une capacité doit préciser agent de construction, runtime application, utilisateur final ou infrastructure de développement. Le même provider peut avoir plusieurs configurations indépendantes.
2. **Séparer définition, connexion et liaison.** Catalogue de capacités, credentials/configuration, rattachement projet et opération attestée doivent avoir des identifiants et cycles de vie distincts. Un annuaire MCP ajoute de la découverte, pas une preuve d’exécution.
3. **Afficher l’état réel et sa portée.** Proposé, configuré, authentifié, accessible, invoqué, vérifié ; avec identité, source, révision, date, résultat et limites. Une attestation du host ne devient pas automatiquement une capacité de l’application exportée.
4. **Éviter d’imiter une passerelle inexistante.** OAuth utilisateur final, renouvellement, stockage des secrets, contrôle de session, quotas et relais runtime sont une infrastructure à concevoir et exploiter. Une fiche de connecteur ou un ticket d’exécution ne les remplace pas.
5. **Rendre les permissions lisibles.** Séparer lecture, mutation, déploiement, facturation et destruction ; indiquer si l’accord vaut une fois, pour une personne/connexion/projet, ou au workspace. Décrire l’effet d’une révocation sur sessions, jobs et app publiée.
6. **Maintenir les preuves par révision.** Les scans périmés, tests non exécutés et domaines non pris en charge doivent rester explicites. Distinguer aperçu, snapshot prêt, adoption et publication ; une synchronisation Git ne vaut pas publication.
7. **Préserver la reprise locale.** L’import d’un dépôt existant est une différence documentée de périmètre. Garder inventaire sourcé, inconnues, stack d’origine, sources exportables et absence de build simulé ; ne pas copier la limitation d’import de Lovable par accident.
8. **Organiser l’UI par contexte.** Bibliothèque/workspace pour réutilisation et politiques ; projet pour implémentation et preuves ; application pour runtime ; compte pour préférences personnelles. Une capacité indisponible doit expliquer le prérequis concret, sans générer une fausse connexion.

Les investigations suivantes, si décidées, seraient des essais ciblés sur comptes/projets autorisés : consentement et révocation, séparation des utilisateurs, isolation des secrets, action réellement exécutée, répétition d’une mutation et révocation après publication. Elles n’ont pas été réalisées dans cette recherche.
